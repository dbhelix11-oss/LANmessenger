lanmessenger — Deploying an Update to the Relay

Take a newly committed build, install it on the Raspberry Pi relay, and independently verify its certificate from a second computer before trusting it.

This walks through the full loop for shipping a code change to the relay (lanmsg-server) that's already running in the house: build it from a specific commit, copy it to the Pi, install it in place of the running binary, and confirm the relay is healthy afterward. The last part covers the step this project's trust model actually depends on — verifying the relay's TLS certificate fingerprint from a machine other than the one you built or deployed from, so trust in the relay never rests on a single computer or a single network hop.

What "signing the certificate" means here. lanmessenger doesn't use a certificate authority — the relay generates its own self-signed TLS certificate the first time it runs, and every client pins its SHA-256 fingerprint on first connect (trust-on-first-use, the same model SSH uses for host keys). There's no CA step to run. "Signing" in practice means independently confirming that fingerprint from a second source — if an attacker can only intercept traffic on one of the two machines you check from, the two fingerprints won't match, and you'll know before any client ever connects to a tampered relay.

Before you start

You'll be touching three different machines in this walkthrough — keep them straight, since the whole point of the last step is that they're independent of each other:

MachineRole
Build machineYour desktop — has the git checkout, builds the new binary.
The relayThe Raspberry Pi — receives and runs the new binary.
Verification machineA third, separate computer (a laptop, a phone with an SSH/OpenSSL-capable terminal app, another desktop) — fetches the relay's certificate independently, to compare against what the relay reports about itself.

Tip. The verification machine doesn't need lanmessenger installed at all — it only needs openssl, which is preinstalled on virtually every Mac, Linux box, and WSL environment.

You'll also need:

  • SSH access to the Pi with a user that can sudo.
  • The commit you want to deploy, checked out on the build machine (git log -1 to confirm you're where you think you are).

1Build the new version

On the build machine, in the repo checkout, make sure you're on the commit you actually want to ship, then cross-compile for the Pi. The relay is cgo-free (pure-Go SQLite, no C dependencies), so this works with nothing more than a plain Go install — no cross-toolchain needed, even from a completely different OS:

cd LANmessenger
git status               # working tree should be clean
git log -1 --oneline     # confirm this is the commit you mean to deploy

# 64-bit Raspberry Pi OS (Pi 3 / 4 / 5) — on the Pi, `uname -m` says aarch64:
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags="-s -w" \
    -o lanmsg-server-arm64 ./cmd/lanmsg-server

# 32-bit Raspberry Pi OS instead:
CGO_ENABLED=0 GOOS=linux GOARCH=arm GOARM=7 go build -trimpath -ldflags="-s -w" \
    -o lanmsg-server-armhf ./cmd/lanmsg-server

-trimpath -ldflags="-s -w" strips local file paths and debug symbols — smaller binary, nothing that identifies your build machine's filesystem layout.

Sanity check. Run file lanmsg-server-arm64 and confirm it says ELF 64-bit ... ARM aarch64 (or the 32-bit equivalent) — catching a wrong-architecture build here is a lot less annoying than catching it via status=203/EXEC on the Pi later.

2Copy it to the Pi

scp lanmsg-server-arm64 youruser@relay.lan:/tmp/

Swap in the Pi's actual hostname or IP. If you don't remember it, it's whatever you used in ExecStart= / your SSH config when you first set the relay up (see docs/SETUP.md).

3Install it and restart the relay

SSH into the Pi. Installing a new binary over the running one is safe on Linux — the currently-running process keeps using its own file handle until it actually restarts — so there's no need to stop the service first:

ssh youruser@relay.lan

sudo install -m 755 /tmp/lanmsg-server-arm64 /usr/local/bin/lanmsg-server
sudo systemctl restart lanmsg-server

This preserves everything. systemctl restart re-execs the same unit with the same -config /etc/lanmsg/server.toml it always used. The relay only generates a TLS certificate and passphrase verifier when they don't already exist (lanmsg-server setup is a one-time step) — an in-place upgrade like this reuses the existing certificate, database, and config untouched. That means the fingerprint every client already has pinned keeps working with no client-side changes needed, and Step 6 below is normally a no-op you're just confirming, not something you have to act on.

4Confirm the relay came back up healthy

sudo systemctl status lanmsg-server
journalctl -u lanmsg-server -n 20 --no-pager

You should see active (running) and a log line noting the relay is listening. While you're here, ask the relay itself what its current certificate's fingerprint is — you'll need this value in the next step:

sudo -u lanmsg lanmsg-server fingerprint -config /etc/lanmsg/server.toml

This prints something like:

a1:b2:c3:d4:e5:f6:07:18:29:3a:4b:5c:6d:7e:8f:90:...

Keep this terminal open — you'll compare against it in a moment.

5Verify the certificate from another computer

Now switch to the verification machine — not the Pi, and ideally not the build machine either, since the point is to get a second, independently obtained reading of what the relay is actually presenting over the network right now. Fetch its certificate directly with openssl (no lanmessenger install required):

echo | openssl s_client -connect relay.lan:8443 2>/dev/null | \
    openssl x509 -noout -fingerprint -sha256

That prints something like:

SHA256 Fingerprint=A1:B2:C3:D4:E5:F6:07:18:29:3A:4B:5C:6D:7E:8F:90:...

Case doesn't matter, everything else does. openssl prints hex in uppercase; lanmsg-server fingerprint prints it in lowercase. That difference is cosmetic — lowercase the openssl output (or eyeball it letter-by-letter) and compare the colon-separated hex pairs against what Step 4 printed. They must match exactly, byte for byte. If they don't, stop — do not approve this on any client, and see the warning below.

If the two fingerprints don't match. Something between the two machines is intercepting or altering the connection to the relay, or you connected to the wrong host. Do not proceed. Check that relay.lan actually resolves to the Pi from the verification machine's network path (dig relay.lan / nslookup relay.lan), and that nothing upstream (a captive portal, a proxy, a misconfigured router) is terminating TLS on its behalf. Only continue once both machines agree.

6If the fingerprint actually changed

An in-place upgrade (Steps 1–3 above) never changes the certificate — so if you followed those steps exactly, the fingerprint you just verified should be identical to the one every client already has pinned, and there's nothing further to do. This step only applies if you deliberately wiped /var/lib/lanmsg/ or otherwise forced a fresh lanmsg-server setup (a new certificate is generated only then):

  • Every client will see a fingerprint mismatch on its next connection attempt and refuse to proceed automatically — this is correct, expected behavior, not a bug.
  • Give each device's owner the newly verified fingerprint (the one you just confirmed matches from two independent machines) through some channel other than the relay itself — in person, a phone call, a messaging app you already trust. Never just paste it into a channel that itself depends on the relay you're trying to verify.
  • Each client explicitly accepts the new fingerprint when prompted, or clears its stored one and re-enrolls. See docs/SETUP.md's "Verifying contacts" section for the full client-side flow.

Rolling back

Before you overwrite it in Step 3, it's worth keeping the previous binary around in case the new version misbehaves:

# On the Pi, before installing the new one:
sudo cp /usr/local/bin/lanmsg-server /usr/local/bin/lanmsg-server.previous

# If the new version needs to be rolled back:
sudo cp /usr/local/bin/lanmsg-server.previous /usr/local/bin/lanmsg-server
sudo systemctl restart lanmsg-server

Rolling back the binary never touches /etc/lanmsg/ or /var/lib/lanmsg/, so the certificate, passphrase, and message queue are unaffected either way.

Troubleshooting

SymptomCauseFix
status=203/EXEC Wrong architecture, or the binary isn't executable file /usr/local/bin/lanmsg-server — confirm it matches the Pi's real architecture (uname -m); redo Step 1 with the right GOARCH.
Service won't start, log mentions permission denied /etc/lanmsg or /var/lib/lanmsg ownership got clobbered sudo chown -R lanmsg:lanmsg /etc/lanmsg /var/lib/lanmsg
Step 5's two fingerprints don't match See the warning under Step 5 — possible interception, or wrong hostname Do not proceed; investigate before any client connects
openssl s_client hangs or refuses to connect The relay isn't listening, or a firewall blocks port 8443 from the verification machine's network On the Pi: sudo ss -tlnp 'sport = :8443'. From the verification machine: nc -vz relay.lan 8443.
Clients report a fingerprint mismatch after what you thought was a routine upgrade /var/lib/lanmsg/ was wiped or setup got re-run somehow, generating a new certificate Follow Step 6 — this is the fresh-certificate case, not a bug
