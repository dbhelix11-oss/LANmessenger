lanmessenger — Installation Guide

Set up the relay once, then install a client on each computer.

lanmessenger has two parts:

  • The relay (lanmsg-server) — one copy, on a machine that stays on (a Raspberry Pi, a NAS, a spare Linux box). It forwards encrypted messages between clients and holds messages for a computer that is asleep. It cannot read anything it forwards.
  • The client — one per computer people actually use. Either the desktop app (lanmsg) or the terminal client (lanmsg-cli).

The fingerprint. Every client connects to the relay over TLS. The relay creates its own certificate the first time it runs and prints a fingerprint — a short string of hex. Each client shows you that fingerprint on its first connection and asks you to confirm it. Write the fingerprint down when you set up the relay; you need it on every client.

1. Installing Go

You need Go 1.27 or newer to build anything in this project. Check with:

go version

If you get command not found: go, install it as below, then open a new terminal window and try again.

Do not use your package manager's golang package on Debian, Ubuntu, or Raspberry Pi OS — it is usually one or more releases behind and this project needs 1.27+. Use the official tarball or installer.

1.1 macOS

First check your chip:

uname -m

arm64 = Apple Silicon (M1/M2/M3/M4). x86_64 = Intel.

Option A — official installer (simplest)

Download the .pkg from go.dev/dl:

  • Apple Silicon → go1.27.0.darwin-arm64.pkg
  • Intel → go1.27.0.darwin-amd64.pkg

Double-click it, or from the terminal (match arm64/amd64 to your chip):

curl -LO https://go.dev/dl/go1.27.0.darwin-arm64.pkg
sudo installer -pkg go1.27.0.darwin-arm64.pkg -target /

The installer adds /usr/local/go/bin to your PATH via /etc/paths.d/go. That only takes effect in new shells, so open a fresh terminal window, then:

go version        # go version go1.27.0 darwin/arm64

Option B — Homebrew

Only if you already have Homebrew (brew --version works):

brew install go

If you don't have Homebrew, don't install it just for this — the .pkg is quicker.

About xcode-select --install. On macOS you also need the Command Line Tools (they provide clang). If you run xcode-select --install and see "command line tools are already installed", that is not an error — you already have them. Move on.

1.2 Linux (x86-64 desktop)

# 1. download
curl -LO https://go.dev/dl/go1.27.0.linux-amd64.tar.gz

# 2. replace any existing install
sudo rm -rf /usr/local/go
sudo tar -C /usr/local -xzf go1.27.0.linux-amd64.tar.gz

# 3. put it on PATH for all users
echo 'export PATH=$PATH:/usr/local/go/bin' | sudo tee /etc/profile.d/go.sh
source /etc/profile.d/go.sh

# 4. verify
go version

1.3 Raspberry Pi OS

Same as Linux, but pick the ARM tarball. Check the architecture first:

uname -m
# aarch64        -> use linux-arm64
# armv7l / armv6l -> use linux-armv6l
cd /tmp
curl -LO https://go.dev/dl/go1.27.0.linux-arm64.tar.gz       # 64-bit Raspberry Pi OS
# curl -LO https://go.dev/dl/go1.27.0.linux-armv6l.tar.gz    # 32-bit

sudo rm -rf /usr/local/go
sudo tar -C /usr/local -xzf go1.27.0.linux-arm64.tar.gz
echo 'export PATH=$PATH:/usr/local/go/bin' | sudo tee /etc/profile.d/go.sh
source /etc/profile.d/go.sh
go version

You may not need Go on the Pi at all. If the Pi is only going to run the relay, it is easier to cross-compile the binary on your desktop and copy it over. Installing Go on the Pi is only worth it if you want to build there directly.

1.4 Windows

Download the .msi installer from go.dev/dl (go1.27.0.windows-amd64.msi) and run it. It sets PATH for you. Open a new Command Prompt or PowerShell and run go version.

2. The relay

2.1 Get the lanmsg-server binary onto the machine

Two ways. Building on your desktop and copying the binary over is usually less hassle than installing Go on a Pi.

Option A — build on your desktop, copy it over (recommended)

In a checkout of this repo on your desktop:

# Raspberry Pi 3 / 4 / 5 on 64-bit Raspberry Pi OS  (on the Pi, `uname -m` says aarch64):
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags="-s -w" \
    -o lanmsg-server-arm64 ./cmd/lanmsg-server

# 32-bit Raspberry Pi OS:
CGO_ENABLED=0 GOOS=linux GOARCH=arm GOARM=7 go build -trimpath -ldflags="-s -w" \
    -o lanmsg-server-armhf ./cmd/lanmsg-server

# An ordinary x86-64 Linux box:
CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o lanmsg-server ./cmd/lanmsg-server

Why CGO_ENABLED=0? It produces a single self-contained binary with no shared-library dependencies, and it is what lets you build for the Pi from a different kind of machine without a cross-compiler. (The relay uses a pure-Go SQLite, so there is no C code to link.) -trimpath -ldflags="-s -w" just keeps your local paths out of the binary and makes it smaller.

Copy it to the relay and install it (swap in your relay's hostname):

scp lanmsg-server-arm64 stoic@relay.lan:/tmp/
ssh stoic@relay.lan
sudo install -m 755 /tmp/lanmsg-server-arm64 /usr/local/bin/lanmsg-server

Option B — build on the relay machine itself

Needs Go 1.27+ installed on that machine. Then:

git clone https://github.com/dbhelix11-oss/LANmessenger.git lanmessenger && cd lanmessenger
CGO_ENABLED=0 go build -o /tmp/lanmsg-server ./cmd/lanmsg-server
sudo install -m 755 /tmp/lanmsg-server /usr/local/bin/lanmsg-server

Check it either way

lanmsg-server -h        # should print usage text

2.2 Create the config (run once)

setup writes the config file, generates the TLS certificate, and prints the fingerprint.

We put the config in /etc/lanmsg/ and the data (database + certificate) in /var/lib/lanmsg/, both owned by a dedicated lanmsg user that the service will run as:

sudo useradd --system --no-create-home --shell /usr/sbin/nologin lanmsg
sudo install -d -o lanmsg -g lanmsg /etc/lanmsg /var/lib/lanmsg

sudo -u lanmsg lanmsg-server setup \
    -config /etc/lanmsg/server.toml \
    -data   /var/lib/lanmsg \
    -listen 0.0.0.0:8443
PartMeaning
useradd --system … lanmsga locked-down account with no login and no home, just to run the relay
install -d -o lanmsg -g lanmsg …create both directories owned by lanmsg (like mkdir + chown in one)
-listen 0.0.0.0:8443listen on port 8443 on every network the machine has
sudo -u lanmsg …run setup as that user so the files it writes are owned by it

It prompts for the household passphrase twice. Everyone uses this same passphrase to enroll a device; the relay stores only a verifier derived from it, never the passphrase itself. When it finishes it prints:

TLS certificate fingerprint (SHA-256) — every client confirms this on first connect:

  57:be:45:64:34:c8:...:3b:46

Copy that fingerprint somewhere safe. You need it on every client. Lost it later?

sudo -u lanmsg lanmsg-server fingerprint -config /etc/lanmsg/server.toml

2.3 Run it under systemd

The repo ships a unit at deploy/lanmsg-server.service that already matches the paths above.

# copy the unit into place (scp it over, or run from your repo checkout on the relay)
sudo cp deploy/lanmsg-server.service /etc/systemd/system/

# 1. test by hand first — you should see a log line saying it's listening; Ctrl-C to stop
sudo -u lanmsg lanmsg-server run -config /etc/lanmsg/server.toml

# 2. hand it to systemd
sudo systemctl daemon-reload
sudo systemctl enable --now lanmsg-server

# 3. check
systemctl status lanmsg-server
journalctl -u lanmsg-server -f

enable --now starts it now and makes it start again after a reboot. If status shows activating (auto-restart) with an error, see Troubleshooting — the two usual causes are "binary not where the unit expects it" and "setup was never run".

2.4 Docker alternative

cd deploy
docker compose run --rm relay setup -config /data/server.toml -data /data -listen 0.0.0.0:8443
docker compose up -d
docker compose run --rm relay fingerprint -config /data/server.toml   # print the fingerprint

docker-compose.yml uses host networking and keeps everything under ./data.

2.5 Admin approval (optional)

By default, anyone who has the passphrase and can reach the relay is admitted automatically. To instead require that an existing trusted device approve each new one:

  • pass -approval to setup, or
  • set require_admin_approval = true in server.toml and restart the service.

The first device to enroll is always admitted and becomes an admin — even with approval on — so you cannot lock yourself out. After that, each new device sits in a "pending" state until an admin approves it from the desktop app's Pending devices panel.

3.1 Prerequisites per OS

After installing Go, the desktop app also needs a C compiler. The GUI toolkit (Fyne) links native graphics code.

Debian / Ubuntusudo apt install gcc pkg-config libgl1-mesa-dev xorg-dev libxkbcommon-dev
Fedorasudo dnf install gcc pkgconf-pkg-config mesa-libGL-devel libX11-devel libXcursor-devel libXrandr-devel libXinerama-devel libXi-devel libxkbcommon-devel
macOSCommand Line Tools: xcode-select --install ("already installed" is fine). No extra libraries — Fyne uses frameworks built into macOS.
WindowsA MinGW-w64 gcc (via MSYS2), or cross-build with fyne-cross (see 3.4).

3.2 Build the desktop app

git clone https://github.com/dbhelix11-oss/LANmessenger.git
cd LANmessenger

go build -o lanmsg ./cmd/lanmsg        # or run it directly: go run ./cmd/lanmsg
./lanmsg

That is all you need to run the app on the machine you built it on.

3.3 The terminal client

CGO_ENABLED=0 go build -o lanmsg-cli ./cmd/lanmsg-cli

./lanmsg-cli enroll -server relay.lan:8443 -name "Dad's laptop"
./lanmsg-cli roster
./lanmsg-cli send -to "Mom's laptop" -text "dinner in 10"
./lanmsg-cli status dnd
./lanmsg-cli watch            # stay connected, print incoming messages / presence

3.4 Make a double-clickable bundle

Use the fyne packaging tool:

go install fyne.io/tools/cmd/fyne@latest

fyne: command not found? go install puts the tool in $(go env GOPATH)/bin (usually ~/go/bin), which is probably not on your PATH. Add it:

export PATH="$PATH:$(go env GOPATH)/bin"

(put that line in ~/.bashrc or ~/.zshrc to make it stick), or call it by full path: ~/go/bin/fyne …

App metadata (name, icon, ID, version) lives in cmd/lanmsg/FyneApp.toml, so packaging is one command run from that directory:

cd cmd/lanmsg
fyne package -os linux         # -> lanmessenger.tar.xz

You package for an OS on that OS. Fyne needs a C compiler that targets the destination, and fyne package does not ship cross-toolchains.

TargetWhere to run it
Linux tarballon Linux: cd cmd/lanmsg && fyne package -os linux
macOS .appon a Mac (after xcode-select --install): cd cmd/lanmsg && fyne package -os darwin
Windows .exeon Windows (MSYS2 + MinGW): fyne package -os windows
or from Linux with fyne-cross (Docker): 
sudo apt install gcc-mingw-w64
go install github.com/fyne-io/fyne-cross@latest
fyne-cross windows -arch amd64 ./cmd/lanmsg

Cross-building a macOS .app from Linux is not practical — it needs the Apple SDK. Build it on a Mac.

Gatekeeper. When you copy an unsigned lanmessenger.app to another Mac, macOS quarantines it. On that Mac, either right-click the app → Open the first time, or run:

xattr -dr com.apple.quarantine /path/to/lanmessenger.app

4. First run & enrollment

The desktop app opens a short wizard:

  1. Relay address — e.g. relay.lan:8443 or 192.168.1.10:8443.
  2. Confirm the fingerprint — the app shows the certificate fingerprint it received from the relay. Check it against what setup printed. Match → continue. No match → stop (see Troubleshooting).
  3. Display name and passphrase — a name for this device ("Dad's laptop") and the household passphrase.
  4. If the relay uses admin approval and this isn't the first device, you land on a "waiting for approval" screen until an admin approves you.

The terminal client does the same in one command:

lanmsg-cli enroll -server relay.lan:8443 -name "Dad's laptop"
# fetches the fingerprint, shows it, asks you to confirm, then prompts for the passphrase

Config, keys and history live in your OS config directory:

OSPath
Linux~/.config/lanmessenger
macOS~/Library/Application Support/lanmessenger
Windows%AppData%\lanmessenger

Pass -config <dir> to any client to use a different directory (useful for running two identities on one machine while testing).

5. Verifying contacts

TLS and the certificate fingerprint protect the hop between a client and the relay. They do not prove that "Mom's laptop" in your roster is really Mom's — the relay operator, or anyone who learned the passphrase, could enroll a device under any name.

So each device also has its own short key fingerprint (desktop app: Settings → This device's fingerprint). A newly seen person shows in your roster as unverified. To verify: have them read their fingerprint aloud — across the house, over the phone — compare it to what your client shows for them, and click verify.

If a contact's fingerprint ever changes (reinstall, new machine, or something wrong), the client flags it and you verify again.

Always reproduce it by hand as the service user before blaming systemd:

sudo -u lanmsg lanmsg-server run -config /etc/lanmsg/server.toml

A client reports a fingerprint mismatch

The fingerprint the client now sees differs from the one it pinned on first connect. Usually one of:

  • The relay's certificate was regenerated — its data dir was wiped, or setup was re-run. Every client has to re-confirm: accept the new fingerprint when prompted, or clear the stored one in the client's config dir and re-enroll.
  • You're connecting to the wrong host — a different machine answered on that address.
  • Something is intercepting the connection — if neither of the above fits, stop and investigate.

A client connects from one part of the house but not another

That's network routing, not lanmessenger — the relay has to be reachable from both subnets. See docs/NETWORK.md for where to place the relay and the static route a two-router setup needs.

connection refused from every client

The relay isn't listening, or a firewall blocks the port. On the relay: systemctl status lanmsg-server, then ss -tlnp 'sport = :8443'. From a client: nc -vz relay.lan 8443.
